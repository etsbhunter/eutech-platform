## Phase 3 — Catalogue, pricing and subscription core — DONE

- `prisma/seed.ts` seeds Eutech Clinic's Starter/Professional/Enterprise plans with placeholder monthly+annual prices (`isPlaceholder: true`) and features (branch limit, staff seats, support level, integrations); Enterprise intentionally has no self-serve price row.
- `GET /api/v1/catalogue/plans` (public) serves that catalogue to the frontend — the pricing page fetches it at runtime instead of hardcoding numbers, while plan/feature *display copy* stays in `next-intl` translation keys matched by slug. This satisfies the master brief's "database/config driven, not hardcoded" requirement while keeping all user-visible text translatable.
- `BillingProvider` abstraction (`billing-provider.interface.ts`) with `FakeBillingProvider` (local/dev, no network calls) and `LemonSqueezyBillingProvider` (real HMAC-SHA256 webhook signature verification against the raw request body, status mapping; checkout/portal API calls structured against LemonSqueezy's documented shape but not exercised against a live account — no credentials available in this environment).
- `WebhookProcessorService` is the single idempotent processing path both providers funnel through: persists `WebhookEvent` keyed on `[provider, providerEventId]` before doing anything else, catches the unique-constraint violation to detect a safe replay, and only then upserts the `Subscription`/`Entitlement`. LemonSqueezy's payload has no documented distinct event-ID field, so its `providerEventId` is a SHA-256 hash of the verified raw body (a genuine retry resends byte-identical content).
- `POST /billing/checkout` and `POST /billing/portal` are tenant-isolated (only an `ORGANIZATION_OWNER`/`BILLING_ADMIN` member of the target organization may call them) and gated behind `AccessTokenGuard`.
- `POST /billing/fake/complete-checkout` simulates the fake provider's "webhook" for local development — refuses to run unless `BILLING_PROVIDER=fake`, and access is still only ever granted by this explicit server-side call, never by the browser redirect to `/checkout/fake` landing.
- `GET /organizations/:id/subscription` (tenant-isolated, same guarantee as the org lookup) backs the account page's subscription display.
- Frontend: pricing page fetches the catalogue and initiates checkout (redirecting unauthenticated visitors to register-with-return-url, users without an organization to `/account`); `/checkout/fake` and `/account/billing/fake-portal` are the local stand-ins for LemonSqueezy's hosted pages; the account page shows subscription status and a "Manage billing" button wired to the portal endpoint.

**Verified**: backend `pnpm exec jest` (48/48 passing, including webhook idempotency, signature verification against forged/wrong-secret/missing-header cases, and checkout authorization) and `pnpm exec eslint` clean; frontend `pnpm exec next build` (18 pages × 2 locales, all static) and `pnpm exec eslint` clean. Full live end-to-end pass against the real database: catalogue endpoint returns seeded plans with Enterprise correctly having no price; checkout blocked for non-members (404) and non-owner/billing-admin roles (403); subscription status is `null`/no-entitlement before checkout and flips to `ACTIVE` only after the fake provider's completion call (never from the redirect alone); replaying the identical fake completion is detected as a duplicate; a genuinely forged LemonSqueezy webhook signature is rejected with 401 while a correctly HMAC-signed payload is accepted, resolves its plan via `Price.providerPriceId`, activates the subscription, and a byte-identical replay is detected as a duplicate. One real bug was caught and fixed during this verification: the webhook receiver was initially using whichever provider was "active" for checkout (fake, in dev) instead of always verifying against LemonSqueezy specifically, which masked signature-rejection behavior — fixed by always injecting `LemonSqueezyBillingProvider` directly for the webhook path.

## Phase 4 — Clinic onboarding and provisioning — DONE

- `PUT/GET /organizations/:id/clinic-profile` — tenant-isolated (same not-found-either-way guarantee as the org lookup), edit restricted to `ORGANIZATION_OWNER`/`PRODUCT_ADMIN`, backs the `/account/onboarding` wizard page (clinic identity, address, branch count, operating hours, staff estimate — integrations deferred, not part of the `ClinicProfile` schema).
- `ProvisioningAdapter` interface (`provisioning-adapter.interface.ts`) mirrors the *proposed* clinic-platform contract from `PROVISIONING_CONTRACT.md`; `MockProvisioningAdapter` is the only implementation (a real adapter can't exist until clinic-platform builds the endpoint). It simulates a realistic `queued → provisioning → ready` lifecycle over a configurable delay (`MOCK_PROVISIONING_DELAY_MS`) rather than resolving instantly, so the "never ready prematurely" gating actually gets exercised.
- `ProvisioningService.requestProvisioning` gates on three things in order: real membership with the right role → a saved `ClinicProfile` exists → an active `Entitlement` exists (i.e. checkout must be complete first) — verified live, each gate independently.
- Retry-safe by construction: `ProductInstance` has a unique `[organizationId, productId]` constraint; a request while already `QUEUED`/`PROVISIONING`/`READY` returns the existing record without calling the adapter again or creating a duplicate row; a request against a `FAILED` instance reuses the same `provisioningRequestId` (the idempotency key that would be sent to a real clinic-platform endpoint) rather than starting a fresh one.
- `GET /organizations/:id/provisioning` both reports and advances the state machine: while `QUEUED`/`PROVISIONING`, it calls the adapter's `checkStatus` and persists any transition; `workspaceId`/`accessUrl` are only ever written when the adapter reports `ready` with both present.
- Frontend: `/account/onboarding` saves the clinic profile then triggers provisioning; the account dashboard polls provisioning status every 2.5s while in flight and only renders the "Open Eutech Clinic" button once `status === READY` and `accessUrl` is set, per acceptance scenario 15.

**Verified**: backend `pnpm exec jest` (62/62 passing, including the full gate/idempotency/retry matrix for provisioning and clinic-profile role checks) and `pnpm exec eslint` clean; frontend `pnpm exec next build` (19 pages × 2 locales, all static) and `pnpm exec eslint` clean. Full live end-to-end pass against the real database with a shortened mock delay: provisioning correctly blocked with 400 before a clinic profile exists and 403 before an active subscription exists; after checkout completion, requesting provisioning returns `PROVISIONING` with `workspaceId`/`accessUrl` both `null`; polling immediately after still shows `PROVISIONING` (not prematurely ready); re-requesting while in-flight is a no-op; after the mock delay elapses, status flips to `READY` with a stable `workspaceId`/`accessUrl` that doesn't change on repeated polls; re-requesting while `READY` is also a no-op. Tenant isolation verified live on all four new endpoints (clinic-profile GET/PUT, provisioning GET/POST) — a second user gets an identical 404 for another organization's data.

## Phase 5 — Eutech Admin and hardening — DONE (core scope)

- **Authorization model**: there is no separate "staff" table. A user is an Eutech internal admin if they hold an `EUTECH_INTERNAL_ADMIN` membership in any organization (`AdminGuard`, checked after `AccessTokenGuard`). `prisma/seed.ts` creates one local dev admin account (`admin@eutech.internal`) with such a membership in a seeded "Eutech Internal Operations" organization — mirrors clinic-platform's own documented demo-credential pattern, local dev only.
- `GET /admin/dashboard` — counts for demo requests, trialing/active/past-due subscriptions, and failed provisioning instances, each an independent `count()` query.
- `GET /admin/organizations` (search by name or owner email, paginated `skip`/`take`, capped at 100) and `GET /admin/organizations/:id` (full detail: memberships, clinic profile, subscriptions, entitlements, provisioning state) — **not** tenant-isolated by design, since this is the cross-organization admin view; access control is entirely `AdminGuard`.
- `GET /admin/demo-requests`, `GET /admin/webhook-events`, `GET /admin/audit-logs` — same search/pagination pattern. Webhook events already never stored raw payloads (see `BILLING_AND_WEBHOOKS.md`), so there is nothing sensitive to redact here.
- `POST /admin/organizations/:id/provisioning/retry` — reuses `ProvisioningService`'s adapter-calling logic via a new `adminRetryProvisioning` method that skips the customer-side membership/role gate (the caller is an Eutech admin, not necessarily an org member) but still refuses to act on anything other than a genuinely `FAILED` instance; writes an `AuditLog` row (`action: "provisioning.retry"`, actor, target) — verified live end-to-end, including the 400 rejection when the instance isn't actually failed.
- `POST /admin/organizations/:id/entitlements` — grants a manual `Entitlement` override; `reason` (min 10 chars) and `expiresAt` (ISO date) are both required by DTO validation, matching the master brief's "reason, actor and expiry" requirement; writes a matching `AuditLog` row. **No endpoint exists anywhere to directly edit `Subscription.status`** — this manual-override path is the only way to grant access outside the normal webhook flow, satisfying acceptance scenario 19 by construction rather than by a runtime check.
- Frontend: `/admin` (dashboard tiles), `/admin/organizations` (searchable, paginated list) and `/admin/organizations/:id` (detail + retry/grant actions), `/admin/demo-requests`, `/admin/audit-logs`, `/admin/webhook-events`. `AdminGuard` (a client component) shows an access-denied message for authenticated non-admins and redirects unauthenticated visitors to login; the "Admin" link in the header only renders for users with an `EUTECH_INTERNAL_ADMIN` membership.

**Verified**: backend `pnpm exec jest` (69/69 passing, including guard authorization, dashboard aggregation, organization search/shaping, and both audited actions) and `pnpm exec eslint` clean; frontend `pnpm exec next build` (24 pages × 2 locales plus one dynamic org-detail route, all clean) and `pnpm exec eslint` clean. Full live end-to-end pass against the real database: a regular customer gets 403 from every `/admin/*` endpoint; the seeded admin can list/search organizations by owner email, view full org detail, grant a manual entitlement (rejected with 400 when the reason is missing, accepted and audit-logged when valid), and retry a manually-marked-`FAILED` provisioning instance (rejected with 400 against a `NOT_STARTED` instance, accepted and audit-logged against a genuinely failed one) — the audit log then correctly shows both actions.

**Not done / explicitly deferred** (scope judgment call given the size of Phases 0-5 already delivered in one pass):
- No dedicated rate-limit/security test *suite* beyond what each module's own tests already cover (auth, webhooks) — a full pass would benefit from being its own reviewed piece of work rather than appended here.
- `DEPLOYMENT_RUNBOOK.md` remains a placeholder — real deployment targets haven't been decided (see that file for the checklist of what's needed).
- Support-ticket module (`docs/SUPPORT_AND_BUG_REPORTING.md`) — schema exists (Phase 0), no business logic. This was always scoped as its own phase-equivalent of work in the master brief, not part of the five suggested phases.
- No end-to-end browser test automation (e.g. Playwright) — all frontend verification in this repository was done via clean builds/lint plus direct API-level live testing of the exact requests each page makes, since no browser automation tool was available in this environment. A real browser QA pass is recommended before shipping.

Additional Eutech products are out of scope until the Eutech Clinic subscription vertical slice is complete and verified, per the master brief.
