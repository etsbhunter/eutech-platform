# Provisioning Contract

## Implementation status

`backend/src/provisioning/` implements this contract's request/response shape and idempotency semantics exactly (see `ProvisioningAdapter` interface), but only against `MockProvisioningAdapter` — the real clinic-platform endpoint described below still does not exist. `ProvisioningService` additionally gates a provisioning request on the caller having a saved `ClinicProfile` and an active `Entitlement`, neither of which is part of the wire contract itself. Verified live end-to-end: gating, idempotent retries, and the `queued → provisioning → ready` state machine with the "never ready without workspaceId+accessUrl" rule.

## Current state (verified against clinic-platform's source)

clinic-platform exposes exactly two relevant endpoints today:

- `GET /api/v1/health` — DB liveness only, not clinic-scoped, touches no clinical data.
- `GET /api/v1/clinics/me` — read-only, returns the *caller's own* clinic (requires an authenticated JWT + `x-clinic-id` header for an existing membership).

**No endpoint exists to create a new clinic tenant.** The only ways a `Clinic` row is created today are a dev seed script (`apps/backend/prisma/seed.ts`) and direct Prisma writes in integration test setup — neither is a safe pattern to expose to an external caller. A `CLINIC_MANAGE` permission is declared in clinic-platform's permission catalog but is not enforced by any controller — it grants nothing today.

## Proposed contract (does not exist yet — requires a separate, explicitly-approved change inside clinic-platform)

```
POST /api/v1/internal/provisioning/clinics        [PROPOSED]
Auth: a new service-to-service credential (e.g. a signed HMAC header or mTLS),
      NOT a user JWT — Eutech is not a clinic-platform user.
Request:
  {
    "eutechWorkspaceRequestId": "uuid",   // idempotency key, generated by Eutech
    "clinicName": "string",
    "ownerName": "string",
    "ownerEmail": "string",
    "defaultLanguage": "en" | "zh"
  }
Response 201: { "clinicId": "uuid", "status": "provisioning" }
Response 200 (replay of the same eutechWorkspaceRequestId): identical body, no duplicate Clinic row.

GET /api/v1/internal/provisioning/clinics/{eutechWorkspaceRequestId}   [PROPOSED]
Auth: same service credential.
Response: { "clinicId": "uuid"|null, "status": "queued|provisioning|ready|failed", "accessUrl": "string|null" }
```

- **Idempotency/retry**: keyed on `eutechWorkspaceRequestId`, which is exactly `ProductInstance.provisioningRequestId` in Eutech's schema. A retried provisioning job never creates a second `Clinic`.
- **Status-check behavior**: Eutech's `ProvisioningStatus` state machine (`NOT_STARTED → QUEUED → PROVISIONING → READY|FAILED`) only advances to `READY` when this endpoint returns a genuine `ready` status **and** a non-null `accessUrl`. The "Open Eutech Clinic" button in the customer portal stays disabled until both are true.

## Identity/handoff for the MVP

Even with Eutech's stack matching clinic-platform's (NestJS/JWT on both sides), clinic-platform has no endpoint today to accept an externally-issued token, and adding one is out of scope for this repository. For the MVP:

1. Eutech's provisioning job calls the proposed internal API to create the clinic + first admin.
2. clinic-platform (on its own side, once it implements this) emails that admin their own clinic-platform credentials or a one-time setup link.
3. The admin ends up with a **separate but linked identity** in clinic-platform — Eutech never stores or has access to the clinic-platform password/token, only `workspaceId`, `accessUrl`, and `provisioningStatus`.

Real single sign-on (clinic-platform accepting an Eutech-issued token) is explicit future work, contingent on clinic-platform's own team adding support on their side.

## Until the proposed endpoint exists

Phase 4 ships behind an internal mock adapter (`PROVISIONING_ADAPTER=mock` in `backend/.env`), so the onboarding wizard, provisioning state machine, and "Open Eutech Clinic" gating can be built and tested now without depending on a change to clinic-platform.
